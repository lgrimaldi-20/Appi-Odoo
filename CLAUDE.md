# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Python/FastAPI middleware between an external system and Odoo ERP. It started as a **generic JSON-RPC proxy** (`POST /odoo` — run any method on any model) and now also provides a **stateful accounting sync layer**: idempotent creation + posting of invoices and payments, reconciliation, tax-total validation, and background processing with retries and logical rollback.

Code comments and log messages are in Spanish; keep that convention. Follow PEP8.

## Architecture

The service is layered. The two original files are the **transport layer**; everything stateful lives under `core/` and `routers/`.

### Transport (unchanged foundation)
- **[odoo_universal.py](odoo_universal.py)** — `OdooUniversalAPI`, a thin JSON-RPC client. Constructor queries `common.version` (best-effort, failure degrades to `version_mayor == 0`) and then logs in immediately via **`common.authenticate`** — `common.login` was removed in Odoo 19 — raising `OdooConnectionError`; `execute(model, method, *args, **kwargs)` calls `execute_kw`. `version` / `version_mayor` expose the detected server series so call sites can branch per version. Typed exceptions: `OdooConnectionError` (network/auth) vs `OdooExecutionError` (Odoo returned an error). Multi-tenant via a module-level `_tenants` dict — `register_tenant()` / `get_tenant()`.
- **[api.py](api.py)** — the FastAPI app. On import: builds the `"default"` tenant from `ODOO_*` env vars (a failed connection is logged, does **not** crash startup — `/health` reports `degradado`), calls `init_db()`, and mounts the business routers. Holds `/odoo` (generic proxy) and `/health`.

### Stateful accounting layer (`core/`)
The invoice/payment flow chains three pieces: **state store** (idempotency) → **mapper** (translate) → **execute** (create + post).

- **[core/state_store.py](core/state_store.py)** + **[core/models_db.py](core/models_db.py)** — the **control database** (SQLAlchemy, separate from Odoo). Two tables: `sync_map` (unique `(entidad, id_origen)` ↔ `id_odoo` + `estado` + `hash_payload`) and `sync_log` (append-only audit). States: `PENDIENTE → PROCESANDO → PROCESADO | ERROR`. `DATABASE_URL` defaults to local SQLite; use PostgreSQL in prod. This is what makes everything idempotent.
- **[core/mapper.py](core/mapper.py)** + **[core/mappings.yaml](core/mappings.yaml)** — declarative mapping from a source record to Odoo values. Applies `defaults`, renames fields, and resolves FKs (`resolver`) by looking up the real Odoo id from a business value (e.g. NIF→`res.partner.vat`). FK resolution doubles as master-data validation. Add/change an entity by editing the **YAML**, not code. Raises `MapeoError`.
- **[core/sincronizador.py](core/sincronizador.py)** — the orchestrator. `sincronizar_entidad(entidad, registro, odoo)`: idempotency check → `PROCESANDO` → map → `create` (id saved immediately) → `action_post` → optional total validation → `PROCESADO`. Every step logs; any failure sets `ERROR` and raises `SincronizacionError`. **Key detail:** if `create` succeeds but `action_post` fails, the `id_odoo` is kept and the error says "created but not posted" — so rollback knows what to compensate.
- **[core/facturacion.py](core/facturacion.py)** / **[core/pagos.py](core/pagos.py)** — thin business wrappers (`crear_factura` / `crear_pago`) over the orchestrator for `account.move` / `account.payment`.
- **[core/conciliacion.py](core/conciliacion.py)** — `conciliar(factura_id_odoo, pago_id_odoo, odoo, ...)`. Reconciles by finding the receivable/payable `account.move.line`s of the invoice and the payment's move and calling `reconcile()`. Idempotent via entity `"conciliacion"` keyed `"<factura>:<pago>"`. Raises `ConciliacionError`. **Note:** it checks `estado == PROCESADO` directly (not `ya_procesado()`) because reconciliation has no single `id_odoo`.
- **[core/impuestos.py](core/impuestos.py)** — `verificar_total()`. Compares Odoo's `amount_total` with the source total using `Decimal` (via `str`, to avoid float noise) and a 1-cent tolerance. Raises `DescuadreError`; the invoice stays `ERROR` (not marked done). Wired into the orchestrator only when the entity's YAML has `validar_total: <campo>`.
- **[core/inventario.py](core/inventario.py)** — stock adjustments. `ajustar_stock(registro, odoo)` resolves the product (`default_code`) and internal location, finds/creates the `stock.quant`, writes `inventory_quantity`, then calls **`action_apply_inventory()`** — the official path, so Odoo generates the traceable `stock.move` instead of silently overwriting a quantity. Modes: `fijar` (absolute count, default) / `incrementar` / `decrementar`; a decrement below zero is refused. Idempotent by the source `ajuste_id` — **essential**, since replaying an `incrementar` would silently corrupt inventory. `consultar_stock()` is the read-only counterpart. Raises `InventarioError`. Note this module does **not** use `mappings.yaml` (its input is a fixed, small schema, not a record translation).

### Queue, retries, rollback (`core/`)
- **[core/celery_app.py](core/celery_app.py)** — Celery config. **Eager mode is automatic when `CELERY_BROKER_URL` is empty** (tasks run inline, synchronously) — that's how tests and dev run without Redis.
- **[core/tasks.py](core/tasks.py)** — background tasks. `sincronizar_factura_task` / `sincronizar_pago_task` retry with exponential backoff **only** on `OdooConnectionError` (not on data errors). `procesar_venta_task` runs the full invoice→payment→reconcile flow and triggers **logical rollback** ([core/rollback.py](core/rollback.py) `cancelar_factura`: `button_draft` + `button_cancel`) if payment/reconciliation fails after the invoice was created. Tasks resolve the tenant by name via `get_tenant` (the connector isn't serializable). `poller_task` is the periodic pull-mode task (see below).

### Poller — modo pull desde la DB del cliente (`core/poller.py` + `core/poller_source.py`)
Alternativa al modo push (cliente hace `POST /facturas`…). Aquí **el cliente no llama al middleware**: deja registros en **su propia base de datos** (p.ej. un RDS PostgreSQL en su cuenta AWS, por aislamiento de seguridad — es dueño de sus datos) y el middleware la **sondea**. Flujo: `Cliente escribe → poller lee (Celery Beat) → sincronizar_entidad → Odoo → escribe resultado de vuelta`.
- **[core/poller_source.py](core/poller_source.py)** — acceso a la DB **de origen** del cliente, con engine **separado** del de control (`SOURCE_DATABASE_URL`, perezoso: sin esa var el modo pull está apagado). Tabla genérica `cola_sincronizacion` (`entidad`, `id_origen`, `payload` JSON en formato de `mappings.yaml`, `estado` PENDIENTE|PROCESADO|ERROR). `tomar_lote()` lee PENDIENTE con `FOR UPDATE SKIP LOCKED` (degradado a SELECT normal en SQLite); `marcar_resultado()` escribe el estado de vuelta — el **único** permiso de escritura que el middleware necesita en la DB del cliente.
- **[core/poller.py](core/poller.py)** — `procesar_lote(tenant, limite)`: toma un lote y por cada fila la despacha con `_despachar()` según su `entidad`: `ajuste_stock` → `ajustar_stock`, `asiento` → `crear_asiento`, y el resto → **`sincronizar_entidad`**. Ese despacho es necesario porque inventario y asientos tienen esquema fijo y **no viven en `mappings.yaml`**; sin él, `sincronizar_entidad` los rechaza con *"sin mapeo definido"* y el modo pull solo admitiría facturas y pagos. Para las entidades del YAML, `sincronizar_entidad` (la misma maquinaria del modo push, así el `sync_map` sigue siendo la fuente de verdad de idempotencia — reprocesar no duplica en Odoo). **Aislamiento de errores:** un fallo de DATOS (`SincronizacionError`) deja esa fila `ERROR` y sigue con el resto; un fallo de CONEXIÓN (`OdooConnectionError`) aborta el lote y se propaga → Celery reintenta la pasada completa. **Doble fuente de verdad resuelta:** la cola dice *qué* enviar, `sync_map` dice *qué ya* se envió.
- **Fallo de conexión después del `create`/`action_post`:** Odoo **no participa en la transacción** del middleware, así que si la red cae tras el `create`, el registro queda vivo en Odoo aunque el proceso aborte. Los **cuatro** módulos que escriben en Odoo (sincronizador, inventario, asientos, conciliación) envuelven su trabajo en `state_store.reserva_liberada_si_cae_odoo()`, que ante `OdooConnectionError` libera la reserva dejándola en **`PENDIENTE`** (no `PROCESANDO`, que `reservar()` rechazaría para siempre, bloqueando la fila de forma permanente), **conservando el `id_odoo`**. El reintento lo detecta y **adopta** ese registro en vez de crear un duplicado, continuando desde el posteo. Ojo: **`action_post` NO es idempotente en Odoo 19** — sobre un asiento ya posteado responde *"El asiento (…) debe ser un borrador"*, así que al retomar se consulta el `state` primero (`_ya_posteado`, que acepta también `in_process`/`paid` porque `account.payment` usa otro vocabulario). Verificado en vivo simulando el corte: 1 sola factura en Odoo y estado final `PROCESADO`.
- **La compensación del descuadre vale para los tres caminos** (endpoint síncrono, tarea Celery y poller), no solo para el pull. Vive en `rollback.compensar_descuadre()`, que decide y cancela; los llamadores solo añaden el texto que devuelve al mensaje de error. Estaba duplicada en `poller.py` y `tasks.py`, y por eso `/facturas` devolvía 422 **dejando el asiento posteado**: una prueba de carga dejó 8 facturas vivas con 24 apuntes contables huérfanos. Un **pago** descuadrado también se cancela, pero con `action_cancel`: `account.payment` no tiene `button_draft`/`button_cancel` (Odoo 19 responde *"the method does not exist"*), de ahí `rollback.cancelar_pago()`.
- **Compensación automática del descuadre:** `validar_total` corre **después** del `action_post`, así que una factura descuadrada queda *posteada* en Odoo (asiento contable real) aunque el middleware la marque `ERROR`. El poller la **cancela** (`rollback.cancelar_factura`: `button_draft` + `button_cancel`) para no dejar contabilidad huérfana esperando revisión manual. Para poder decidirlo, `SincronizacionError` lleva ahora `id_odoo` y `descuadre`. **Solo se compensa el descuadre**, no cualquier error: es el único fallo en que consta que el registro está objetivamente mal — un fallo de `action_post`, por ejemplo, deja la factura en borrador (no contabiliza nada) y puede ser transitorio; un fallo de mapeo no llegó a crear nada. La fila queda en `ERROR` y **no se reintenta sola**: reintentarla recrearía y volvería a cancelar la misma factura en bucle cada 30 s; el cliente corrige el importe en origen y la reencola. Se apaga con `POLLER_CANCELAR_DESCUADRE=false` (leído en cada pasada, no al importar).
- **Programación:** `celery_app.py` registra un `beat_schedule` (`poller-cola-cliente`) **solo si** hay `SOURCE_DATABASE_URL`; intervalo `POLLER_INTERVALO_SEG` (30 s por defecto), `POLLER_TENANT`, `POLLER_LIMITE`. Requiere arrancar Beat: `celery -A core.celery_app.celery_app beat --loglevel=info`.
- **Pasadas simultáneas:** dos pasadas a la vez (el botón «Poller ahora» del panel mientras Beat dispara la suya) compiten por las mismas filas. La perdedora recibe `ReservaOcupada`, que el poller **captura y cuenta como `omitidas`** — no es un fallo de datos, la fila la termina el otro proceso y se deja `PENDIENTE` sin marcar resultado. Sin ese `except`, la excepción salía sin capturar y el panel mostraba **HTTP 500**. El router añade además un `except Exception` que registra la traza y devuelve el motivo, en vez de un «Internal Server Error» desnudo.
- **Disparo manual:** [routers/poller.py](routers/poller.py) expone `POST /poller/ejecutar` (protegido, síncrono) para forzar una pasada sin esperar al tick de Beat — útil desde el panel o en pruebas. → 400 si no hay `SOURCE_DATABASE_URL`, 503 si Odoo está caído.

### Routers (`routers/`)
`/facturas`, `/pagos`, `/conciliar`, `/stock/*` — each protected by the shared **[core/seguridad.py](core/seguridad.py)** (`verify_api_key` reads `API_KEY` from env each call; `resolver_tenant` → 400 on unknown tenant). Extracted to a neutral module so routers don't import `api.py` (avoids a circular import). `/facturas`, `/pagos` and `/stock/ajustar` take an optional `"async": true` field → enqueue and return `{encolado, task_id}` (in eager mode this still runs inline); otherwise synchronous. `api.py` also has `GET /estado/{entidad}/{id_origen}` to read a record's sync state.

### Asientos contables (`core/asientos.py` + `routers/asientos.py`)
Crear y **eliminar** asientos contables (`account.move` tipo `entry`). No pasa por el sincronizador genérico ni por `mappings.yaml` (como `inventario.py`): tiene esquema fijo porque un asiento es un conjunto de apuntes debe/haber que **deben cuadrar**, no una traducción 1:1. `crear_asiento(registro, odoo)`: idempotencia por `asiento_id` → resuelve el diario (por `code`) y cada cuenta de las líneas (por `code`, en un lote) → **valida el cuadre débito=haber con `Decimal` antes de tocar Odoo** → `create` (`move_type='entry'`) → `action_post` (salvo `postear: false`, que lo deja en borrador). `eliminar_asiento(asiento_id | id_odoo, odoo)`: un asiento **posteado** no se puede borrar, así que lo lleva a `button_draft` y luego `unlink`; marca el mapeo `ELIMINADO` en el state store. Raises `AsientoError` (→ 422). Endpoints: `POST /asientos` y `DELETE /asientos`. **Nota de formato:** el dominio de `search_read` aquí va como `[["code","=",v]]` (un nivel), no `[[["code","=",v]]]` — el doble anidamiento provoca `tuple index out of range` contra Odoo (mismo bug del commit 6076e1b). Añadido el estado `ELIMINADO` a `EstadoSync` y a las tarjetas del panel.

### Panel de observabilidad (`core/observabilidad.py` + `routers/panel.py`)
Dashboard de **solo lectura** sobre la base de control (`sync_map`/`sync_log`), servido por el propio FastAPI. `core/observabilidad.py` es el reverso de `state_store`: `resumen()` (agregados por estado/entidad), `listar_sincronizaciones()`/`listar_logs()` (con filtros), `detalle_registro()`. `routers/panel.py` expone `GET /panel` (dashboard HTML autocontenido, sin dependencias externas) y los endpoints de datos `GET /panel/api/{resumen,sincronizaciones,logs,detalle/...}`. Las tablas **paginan** con `limite`/`offset` (la respuesta trae `total` junto a `items`, y el tope por página es 500): sin ello el panel solo mostraba los primeros 100 registros y el resto era inalcanzable — con 338 registros de una tanda de pruebas no había forma de llegar a los más antiguos. Los filtros vuelven a la página 1, y un `offset` pasado del final retrocede a la última en vez de mostrar una tabla vacía. **Seguridad:** los endpoints de datos van protegidos por `verify_api_key` (`panel.datos`); la página `/panel` es solo el shell HTML y su JS pide la API Key y la envía como `X-Api-Key` en cada `fetch`. El panel refleja lo que hay en la DB de control (idempotencia, errores, auditoría) — no consulta Odoo.

### Endpoints
`/odoo` (generic, auth) · `/facturas` · `/pagos` · `/conciliar` · `/asientos` (POST crear / DELETE eliminar) · `/stock/ajustar` · `/stock/consultar` · `/poller/ejecutar` (pasada manual, auth) · `/estado/{entidad}/{id_origen}` · `/panel` (HTML, no auth) · `/panel/api/*` (JSON, auth) · `/health` (no auth).

Note the whitelists (`ALLOWED_MODELS`/`ALLOWED_METHODS`) only gate the generic `/odoo` endpoint — the business routers call Odoo directly through the connector.

## Odoo 19 compatibility

The middleware targets **Odoo 19** (calls are backwards-compatible with 17/18 unless noted). What had to change, and why:

- **`common.login` was removed** → the connector authenticates with `common.authenticate`, which takes a 4th `{}` (user-agent env) argument. This is the one change that breaks hard on 19 if missed: auth simply fails.
- **Version detection** — `common.version` is queried before login (it needs no auth). Exposed as `version` / `version_mayor`, and surfaced in `GET /health` as `odoo_version`, so you can confirm which series you are talking to without opening Odoo.
- **`account.account.code` is company-dependent** (since 17; strict in 19) — it is stored per company in `code_store` and computed from the active company. A `["code", "in", [...]]` filter is not reliable, so [core/asientos.py](core/asientos.py) `_cache_cuentas` resolves **one account at a time with `=`**, which Odoo does translate to the active company. Costs N calls instead of 1; correctness wins.
- **`stock.quant` needs `inventory_quantity_set: True`** — writing `inventory_quantity` alone no longer marks the count as entered, so `action_apply_inventory()` would adjust against 0 (silently wrong stock). [core/inventario.py](core/inventario.py) sets both fields on create and write.
- **`account.payment` changed its whole lifecycle** — 17/18 was `draft → posted → cancelled`; **19 is `draft → in_process → paid → canceled | rejected`** (`posted` no longer exists). Crucially, a payment in `in_process` has **`move_id = False`**: it has no journal entry, so there are no `account.move.line`s to reconcile. Verified against a live 19 instance: after `action_post`, after `action_validate`, and even via the native `account.payment.register` wizard, no `account.move` is ever created for the payment. [core/conciliacion.py](core/conciliacion.py) therefore picks its mechanism at runtime: **(A)** if the payment has a `move_id`, the classic `reconcile()` over lines (17/18); **(B)** if not, it links the *existing* payment to the invoice by writing `invoice_ids` with a `(4, id)` command, leaving the invoice in `payment_state = 'in_payment'`. The result dict reports which one ran in `mecanismo` (`apuntes` / `vinculo_pago`). **Do not use `account.payment.register` for this** — that wizard *creates a new payment*, so pairing it with a payment already created by `/pagos` silently duplicates the amount (observed and reverted during testing).
- **`reconcile()` rejects draft entries** — [core/conciliacion.py](core/conciliacion.py) filters `parent_state = 'posted'` in the line domain, so an unposted invoice/payment produces the clear "verify both are posted" error instead of a raw Odoo failure.
- **`account.payment` needs an explicit `partner_type`** to resolve the counterpart account; added as a default in [core/mappings.yaml](core/mappings.yaml) (`customer` for the inbound-payment entity).
- **Domain nesting** — `search_read` domains go one level (`[["code","=",v]]`), never double-wrapped; the double nesting throws `tuple index out of range` (commit 6076e1b).

- **`load_dotenv()` order** — [api.py](api.py) now calls `load_dotenv()` **before** importing project modules. `core/state_store.py` reads `DATABASE_URL` at import time (module level), so loading the `.env` afterwards silently ignored it and the control DB fell back to the default `control.db`. This bit during 19 testing: runs were writing into the V17 control database.

Covered by [tests/test_odoo19.py](tests/test_odoo19.py). Those tests assert the *protocol and call shape* against mocks. **Verified live against an Odoo 19.0 instance (Odoo.sh, 2026-08-19):** authentication, `/health`, invoice create+post+idempotency, payment create, reconciliation via mechanism B, stock adjustment (fijar/incrementar, negative guard, `stock.move` traceability), journal entry create/post/delete, and the observability panel. The live run is what surfaced the `account.payment` lifecycle change — the mocked tests could not have caught it.

## Concurrency, idempotency and performance

Three design decisions that are easy to undo by accident:

- **Idempotency is claimed by an atomic reservation, not by check-then-act.** `state_store.reservar()` / `reservar_estricto()` INSERT the `(entidad, id_origen)` row in `PROCESANDO` **before** touching Odoo and let the `UniqueConstraint` arbitrate; an `IntegrityError` means "someone else got there first" and raises `ReservaOcupada` → **HTTP 409**. The previous `ya_procesado()`-then-`registrar_mapeo()` sequence left a window in which two concurrent requests with the same `id_origen` both read "not processed" and **both created the record in Odoo** — reproduced against the live instance: 6 concurrent calls produced 2 duplicate invoices and 3 × 500. After the fix the same test yields 5 × 409 + 1 × 200 and a single invoice. `reservar_estricto()` is the variant for entities whose `id_odoo` is legitimately `None` (`conciliacion`). Never reintroduce a "read state, then write state" pair around an Odoo write.
- **The connector reuses one `requests.Session`** (`self._session`, with an `HTTPAdapter` pool). Each `requests.post()` used to redo the TCP+TLS handshake: measured 868 ms → 212 ms per call against Odoo.sh. Combined with the FK cache, an invoice went from **3500 ms to ~680 ms (−81%)**. Tests must patch `requests.Session.post`, not `odoo_universal.requests.post`.
- **Master-data lookups are cached** in `core/mapper.py` (`_cache_fk`, TTL 300 s), keyed by `odoo.clave_tenant` (`url|db|uid`) — *not* `id(odoo)`, which CPython recycles, so a fresh connector could inherit a dead one's entries and return ids from another database. Only hits are cached (a miss may be a master record about to be created). `core/asientos.py` reuses the same cache, which matters because company-dependent `code` forces one call per account. `tests/conftest.py` clears it between tests.

## Security & error codes

Security layers, all `.env`-driven and **no-ops when their var is empty**: `API_KEY` (empty → endpoint unprotected, dev mode), `ALLOWED_MODELS` / `ALLOWED_METHODS` (comma-separated whitelists, enforced inside `OdooRequest`'s `field_validator`s → 422), rate limit fixed at `60/minute` per IP (slowapi).

Error mapping: `401` bad/missing API key · `409` `ReservaOcupada` (same `id_origen` already being processed) · `422` whitelist rejection, `OdooExecutionError`, `SincronizacionError`, `ConciliacionError`, `DescuadreError` · `429` rate limit · `503` `OdooConnectionError` · `400` unknown tenant · `500` other.

## Adding capabilities

- **New model/method for `/odoo`:** edit `ALLOWED_MODELS` / `ALLOWED_METHODS` in `.env`.
- **Document types** (`account.move`): the four `move_type`s are declared as **separate entities** in the YAML — `factura` (`out_invoice`), `nota_credito` (`out_refund`), `factura_proveedor` (`in_invoice`), `nota_debito` (`in_refund`) — and selected with the `tipo` field of `POST /facturas` (default `factura`, so existing integrations keep working). They are separate entities *by design*: `move_type` decides the **sign** of the accounting entry, so if the type travelled as one more field and arrived empty or misspelled, the default would apply and a refund would post as a sale — leaving the customer owing the amount instead of being credited, with no visible error. `core/facturacion.py` whitelists them in `ENTIDADES_DOCUMENTO` (an unknown type raises, and `pago` cannot be smuggled through `/facturas`). Purchase documents resolve the partner from `proveedor_nif`; Odoo picks the journal itself from `move_type`. Verified live: `RINV`/`BILL`/`RBILL` sequences with `amount_total_signed` correctly inverted.
- **Taxes travel by name, not by id.** A line may carry `"impuestos": ["15%"]` instead of `tax_ids`; `core/mapper.py` resolves it to the real id, **filtering by `type_tax_use`** derived from the document's `move_type`. That filter is not optional: a typical chart has the same tax name twice (one `sale`, one `purchase`), so resolving by name alone puts output VAT on a supplier bill. A missing tax raises `MapeoError` rather than being skipped — silently dropping it would change the document total. Lines that already carry `tax_ids` are passed through untouched, so existing integrations keep working. Resolutions are cached like any other master-data lookup.
- **`validar_total` is per entity, and so is the Odoo field it reads.** `account.move` stores the amount in `amount_total`, but `account.payment` has no such field — it uses `amount`. The YAML declares `campo_total_odoo` (default `amount_total`), and `verificar_total()` takes `model_odoo`/`campo_odoo`. Payments now validate too: a mis-keyed amount used to sync silently and then reconcile against the invoice leaving a wrong residual. A payment mismatch raises with `descuadre=True`, so the poller compensates it exactly like an invoice.
- **New mapped entity (or change a field mapping):** edit [core/mappings.yaml](core/mappings.yaml). `id_origen` names the source-record key used for idempotency; `resolver` entries look up FKs; optional `validar_total` enables the tax-total check.
- **Add a tenant:** `register_tenant(name, OdooUniversalAPI(...))` at startup in [api.py](api.py); clients pass `"tenant": "<name>"`.

## Tests

HTTP tests ([tests/test_api.py](tests/test_api.py), [tests/test_routers.py](tests/test_routers.py)) patch `OdooUniversalAPI._login` **before importing api.py** and set dummy `ODOO_*` env vars, so no real Odoo connection is made. `core/` unit tests isolate the state store by pointing `DATABASE_URL` at a temp SQLite file (via `monkeypatch.setenv` + `importlib.reload(state_store)`) and mock the `odoo` connector.

**Gotcha:** do **not** `importlib.reload(core.tasks)` in a fixture — it re-registers the Celery tasks and corrupts global state across tests (this caused rollback tests to pass in isolation but fail in the full suite). Patch dependencies by name with `monkeypatch` instead (auto-reverted). When mocking a function a router imported by name (`from core.facturacion import crear_factura`), patch it **on the router module** (`routers.facturas.crear_factura`), not on the source module.

## scripts/ — standalone Odoo utilities (not part of the API)

CLI tools that call the running middleware over HTTP (they read `API_KEY` from env or by parsing `.env`). `excel_a_odoo.py` ↔ `generar_excel_demo.py` do bidirectional Excel⇄Odoo sync on `res.partner` (rows with an ID → `write`, without → `create`). `borrar_duplicados.py` supports `--dry-run`. These require the server running.
